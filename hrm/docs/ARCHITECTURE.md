## 2. หลักการออกแบบ 6 ข้อ

### 2.1 ข้อมูลบุคลากรครั้งเดียว ใช้ได้ทุกกระบวนงาน

`employees` เป็นแหล่งข้อมูลกลางเพียงแห่งเดียว ทุกโมดูลอ้างผ่าน `employee_id`
ไม่มีการคัดลอกชื่อ/ตำแหน่งไปเก็บซ้ำ ยกเว้นสองกรณีที่ตั้งใจ:

| กรณี | เหตุผล |
|---|---|
| `payroll_slips` เก็บ snapshot ชื่อ/ตำแหน่ง/สังกัด | สลิปต้องสะท้อนข้อเท็จจริง ณ วันจ่าย แม้ภายหลังย้ายหน่วยงาน |
| `issued_documents.content_snapshot` | หนังสือรับรองที่ออกไปแล้วต้องตรวจสอบย้อนหลังได้ตรงกับตัวเอกสาร |

### 2.2 ตำแหน่งเป็นข้อมูลตามช่วงเวลา ไม่ใช่ค่าปัจจุบัน

จุดนี้เป็นหัวใจของการรองรับหลายหน่วยงาน `employment_assignments`
เก็บ **หนึ่งแถวต่อหนึ่งช่วงเวลา** ที่บุคคลดำรงตำแหน่งหนึ่ง:

```
พนักงาน A
├─ 2568-07-20 → 2569-08-23  พยาบาลวิชาชีพ  ระดับปฏิบัติการ  รพ.ชุมชน   18,000
└─ 2569-08-24 → (ปัจจุบัน)   พยาบาลวิชาชีพ  ระดับชำนาญการ   รพ.ชุมชน   24,000
```

ทำให้ตอบคำถามเหล่านี้ได้โดยไม่ต้องเดา:
- เดือนที่แล้วคนนี้สังกัดหน่วยงานไหน (ใช้คิดเงินเดือนย้อนหลัง)
- หน่วยงานนี้เมื่อปีที่แล้วมีกี่คน
- ใครเคยอยู่ใต้บังคับบัญชาของหัวหน้าคนนี้บ้าง

ดัชนีเฉพาะ `uq_assign_current_primary` บังคับว่าหนึ่งคนมีตำแหน่งหลักที่ยัง
ไม่ปิดได้เพียงแถวเดียว จึงไม่มีทางเกิดข้อมูลซ้อนกัน

`v_employee_current` คือมุมมองที่ join แถวปัจจุบันมาให้แล้ว —
เกือบทุกหน้าจอและรายงานใช้ view นี้เป็นฐาน

### 2.3 ตรรกะที่ห้ามพลาดครึ่งทาง อยู่ในฐานข้อมูล

Apps Script ไม่มี transaction ข้าม HTTP request การทำงานที่ต้อง
“สำเร็จทั้งหมดหรือไม่สำเร็จเลย” จึงเขียนเป็น RPC:

| RPC | ทำอะไรในคราวเดียว |
|---|---|
| `fn_hire_applicant` | สร้าง employee + assignment + timeline + โอนประวัติการศึกษา/ประสบการณ์ + ปรับสถานะใบสมัคร |
| `fn_submit_leave_request` | ตรวจอายุงาน/เอกสารแนบ/การลาซ้อน/สิทธิคงเหลือ + นับวันตัดวันหยุด + ออกเลขที่ + สร้างคำขออนุมัติ |
| `fn_act_leave_request` | เดินสายอนุมัติทีละขั้น + ปรับสถานะใบลา + คำนวณสรุปเวลาใหม่ในช่วงที่ลา |
| `fn_apply_career_movement` | ปิด assignment เดิม + เปิดใหม่ + บันทึก timeline + บันทึกประวัติเงินเดือน |
| `fn_complete_separation` | ตรวจของค้างคืน + ปิด assignment + ปรับสถานะ + ปิดบัญชีผู้ใช้ + ปิดสิทธิสวัสดิการ |

ส่วนตรรกะที่แต่ละองค์กรมักปรับแต่ง (เช่นสูตรเงินเดือน) อยู่ฝั่ง Apps Script
เพราะแก้ง่ายกว่าและไม่ต้อง migrate ฐานข้อมูล

### 2.4 บังคับสิทธิที่จุดเดียว

Apps Script เรียก Supabase ด้วย `service_role` key ซึ่ง **ข้าม RLS**
ดังนั้น `02_Auth.gs` จึงเป็นด่านเดียวที่ตัดสินว่าใครทำอะไรได้:

```javascript
'leave.act': {
  perm: 'leave.approve',        // router ตรวจสิทธิให้ก่อนเข้า fn
  fn: function (p, ctx) {
    Auth.requireEmployee(ctx, lr.employee_id);   // ตรวจขอบเขตเพิ่มในระดับแถว
    ...
  }
}
```

ทุกเส้นทางประกาศ `perm` ไว้ในตารางเส้นทาง ทำให้ตรวจได้ด้วยสายตาว่า
API ไหนต้องการสิทธิอะไร และสคริปต์ `check_wiring.js` ตรวจอัตโนมัติว่า
รหัสสิทธิที่โค้ดอ้างถึงมีอยู่จริงในตาราง `permissions`

RLS ใน `13_rls.sql` เป็น **ชั้นที่สอง** ที่ยังไม่ทำงานตอนนี้ (เพราะใช้ service_role)
แต่พร้อมใช้ทันทีเมื่อเปิดให้บุคลากรเข้าตรงผ่าน Supabase Auth จากมือถือ
โดยไม่ต้องแก้โค้ดฝั่ง server เลย

### 2.5 ทุกการเปลี่ยนแปลงถูกบันทึกโดยอัตโนมัติ

`fn_audit_trigger` ติดตั้งบน 60 ตาราง บันทึก old/new เป็น JSONB
พร้อมรายชื่อฟิลด์ที่เปลี่ยนจริง (ข้าม `updated_at`/`updated_by` ที่เปลี่ยนทุกครั้ง)
ตาราง `audit_logs` มี trigger กันการแก้ไข/ลบ — เป็น append-only จริง

แยกจากกันคือ `data_access_logs` ที่บันทึก **การเปิดดู** ข้อมูลส่วนบุคคล
ตามหลัก PDPA — เจ้าของข้อมูลดูได้เองว่าใครเปิดดูข้อมูลของตนเมื่อไร
ผ่าน API `audit.myAccessLog`

### 2.6 หลายองค์กร/หลายสถานบริการตั้งแต่แถวแรก

ทุกตารางธุรกรรมมี `org_id` และตารางที่ผูกกับสถานที่มี `facility_id`
การกรองข้อมูลตามขอบเขตสิทธิทำผ่าน `Auth.scopeFilter()` ที่คืน filter
ต่างกันตามสิทธิของผู้ใช้:

| สิทธิที่มี | เห็นข้อมูล |
|---|---|
| `employee.read_all` | ทั้งองค์กร |
| `employee.read_facility` | เฉพาะสถานบริการที่ได้รับมอบหมาย (`user_roles.facility_id`) |
| ไม่มีทั้งสอง | เฉพาะของตนเอง |

การให้สิทธิใน `user_roles` ระบุขอบเขตได้ถึงระดับหน่วยงาน และมีวันเริ่ม-สิ้นสุด
จึงมอบสิทธิชั่วคราว (เช่นช่วงรักษาการ) ได้โดยไม่ต้องจำมาถอนทีหลัง

### 3.4 สายอนุมัติที่ใช้ร่วมกันทุกโมดูล

`approval_flows` / `approval_flow_steps` / `approval_requests` / `approval_actions`
เป็นกลไกกลาง ไม่ผูกกับโมดูลใดโมดูลหนึ่ง — ระบุด้วย `entity_type` + `entity_id`

การเลือกสายอนุมัติอิงเงื่อนไข เช่นใบลาเกิน 5 วันใช้สาย 3 ขั้น
(หัวหน้างาน → หัวหน้ากลุ่มงาน → ผู้อำนวยการ) ส่วนไม่เกิน 5 วันใช้ขั้นเดียว:

```sql
select * from approval_flows
 where entity_type = 'LEAVE_REQUEST'
   and coalesce((condition->>'days_gte')::numeric, 0) <= v_days
 order by coalesce((condition->>'days_gte')::numeric, 0) desc
 limit 1;
```

เพิ่มสายอนุมัติของโมดูลใหม่ได้โดยไม่ต้องแก้โครงสร้างตาราง

## 4. การขยายระบบ

### เพิ่ม API ใหม่

```javascript
// ใน 1x_Api_<Module>.gs
function routesMyModule() {
  return {
    'mymodule.list': {
      perm: 'mymodule.read',
      fn: function (p, ctx) {
        return DB.select('my_table', {
          filter: Auth.scopeFilter(ctx, { module: 'mymodule' })
        });
      }
    }
  };
}
```
แล้วเพิ่ม `routesMyModule` ลงในรายการที่ `buildRoutes()` ใน `04_Main.gs`
router จะโยน error ทันทีถ้าชื่อเส้นทางซ้ำกับของเดิม

### เพิ่มหน้าจอใหม่

```javascript
VIEWS.mymodule = {
  render: function (host, params) {
    return api('mymodule.list').then(function (rows) {
      host.innerHTML = UI.card('หัวข้อ', UI.table([...], rows));
    });
  }
};
```
เพิ่มรายการใน `MODULES` (`00_Config.gs`) เมนูจะขึ้นเองตามสิทธิของผู้ใช้

### เพิ่มรายงานใหม่

เติมรายการใน `REPORT_DEFS` (`23_Api_Report.gs`) — ได้ทั้งหน้าจอ,
ส่งออก CSV และ Google Sheets ในคราวเดียวโดยไม่ต้องเขียนโค้ดเพิ่ม

## 5. เส้นทางต่อยอดเป็นระบบออนไลน์เต็มรูปแบบ

สถาปัตยกรรมนี้ออกแบบให้ย้ายออกจาก Apps Script ได้โดยไม่ต้องเขียนใหม่:

| ขั้น | สิ่งที่ทำ | สิ่งที่ไม่ต้องแก้ |
|---|---|---|
| 1 | เปิด Supabase Auth ให้บุคลากรล็อกอินตรง | สคีมาและ RLS พร้อมอยู่แล้ว |
| 2 | ใส่ claim `org_id` / `employee_id` / `facility_ids` / `perms` ลง JWT | ฟังก์ชัน `auth_*()` ใน `13_rls.sql` อ่านค่าเหล่านี้อยู่แล้ว |
| 3 | ทำแอปมือถือ/เว็บ เรียก PostgREST ตรง | RLS บังคับสิทธิให้เอง ไม่ต้องมี backend |
| 4 | ย้ายงานตามเวลาไปที่ Supabase Edge Functions + pg_cron | RPC ทั้ง 15 ตัวใช้ต่อได้ทันที |

Apps Script ยังคงใช้เป็นหน้าจอสำหรับเจ้าหน้าที่บุคคลได้ต่อไปโดยไม่ขัดกัน

# ความปลอดภัยและการคุ้มครองข้อมูลส่วนบุคคล

ระบบงานบุคคลเก็บข้อมูลอ่อนไหวสูง — เลขบัตรประชาชน เงินเดือน ผลตรวจสุขภาพ
และประวัติวินัย เอกสารนี้อธิบายกลไกป้องกันทั้งหมดและสิ่งที่ผู้ดูแลระบบต้องทำ

---

## 1. การยืนยันตัวตน

ระบบไม่เก็บรหัสผ่านเอง แต่ใช้บัญชี Google ของผู้ใช้:

```
ผู้ใช้เปิดเว็บแอป
   └─► Google ยืนยันตัวตนให้ (SSO ขององค์กร)
        └─► Session.getActiveUser().getEmail()
             └─► เทียบกับ app_users.email หรือ app_users.google_email
                  ├─ ไม่พบ        → ปฏิเสธ + บันทึก login_logs (FAIL_NOT_FOUND)
                  ├─ status ≠ ACTIVE → ปฏิเสธ + บันทึก (FAIL_DISABLED)
                  └─ ผ่าน         → โหลดสิทธิ + บันทึก (SUCCESS)
```

ข้อดี: ไม่มีฐานรหัสผ่านให้รั่ว, ได้ 2FA ขององค์กรมาฟรี, ปิดบัญชีที่ Google
แล้วเข้าระบบไม่ได้ทันที

**การถอนสิทธิ** ทำได้ 3 ระดับ:
1. `app_users.status = 'DISABLED'` — ปิดบัญชีในระบบ HRM
2. ลบแถวใน `user_roles` — ถอนสิทธิบางส่วน
3. ปิดบัญชี Google — ตัดขาดทุกระบบ

เมื่อบุคลากรพ้นสภาพ `fn_complete_separation()` ทำข้อ 1 ให้อัตโนมัติ
พร้อมยกเลิก session ที่ยังไม่หมดอายุ

## 2. โมเดลสิทธิ

### 2.1 โครงสร้าง RBAC + Scope

```
app_users ──< user_roles >── roles ──< role_permissions >── permissions
                  │
                  └── scope: org_id / facility_id / department_id
                             effective_from / effective_to
```

รหัสสิทธิใช้รูปแบบ `<โมดูล>.<การกระทำ>` เช่น `leave.approve`, `payroll.calculate`
มีทั้งหมด 48 รหัส (ดูรายการเต็มใน `14_seed.sql`)

### 2.2 บทบาทมาตรฐาน 8 แบบ

| บทบาท | ขอบเขต | สิทธิเด่น |
|---|---|---|
| `SUPERADMIN` | ทั้งระบบ | `*` (ทุกอย่าง) |
| `HR_MANAGER` | ทั้งองค์กร | ทุกโมดูลยกเว้นระบบ |
| `HR_OFFICER` | ทั้งองค์กร | ทะเบียนประวัติ, ลา, รับสมัคร, อบรม, เอกสาร |
| `PAYROLL` | ทั้งองค์กร | เงินเดือน, สวัสดิการ, ดูข้อมูลบุคลากร |
| `FACILITY_HEAD` | สถานบริการที่ดูแล | อนุมัติลา, ประเมิน, อนุมัติพ้นสภาพ |
| `SUPERVISOR` | ผู้ใต้บังคับบัญชา | อนุมัติลา/เวลา, ประเมินลูกน้อง |
| `EMPLOYEE` | ตนเอง | self-service ทั้งหมด |
| `AUDITOR` | ทั้งองค์กร | อ่านอย่างเดียว + audit log |

### 2.3 การมองเห็นข้อมูลบุคลากร

กติกาเดียวกันทั้งฝั่ง Apps Script (`Auth.canSeeEmployee`) และฝั่งฐานข้อมูล
(`auth_can_see_employee()` ใน `13_rls.sql`):

```
เห็นข้อมูลของบุคลากร X ได้เมื่อ:
  มีสิทธิ employee.read_all                     (HR ระดับองค์กร)
  หรือ X คือตัวเราเอง                            (self-service)
  หรือ X อยู่ในสถานบริการที่เราดูแล + มี employee.read_facility
  หรือ เราเป็นผู้บังคับบัญชาโดยตรงของ X
```

### 2.4 ข้อมูลที่ต้องมีสิทธิเฉพาะเพิ่ม

| ข้อมูล | สิทธิที่ต้องมี | หมายเหตุ |
|---|---|---|
| สลิปเงินเดือน | `payroll.read` | เจ้าตัวดูของตนเองได้เสมอ |
| ผลตรวจสุขภาพ | `health.read` | เจ้าตัวดูของตนเองได้เสมอ |
| ประวัติวินัย | `discipline.read` | เจ้าตัวเห็นเฉพาะเรื่องที่ไม่ตั้งค่าเป็นความลับ |
| แฟ้มเอกสารที่ตั้งเป็นลับ | `employee.read_confidential` | |

## 3. Row Level Security (สองชั้น)

ระบบออกแบบให้ทำงานได้ทั้งตอนนี้และตอนขยายเป็นออนไลน์ โดยไม่ต้องแก้โค้ด

### ชั้นที่ 1 — ปัจจุบัน (Apps Script)

Apps Script เชื่อมด้วย `service_role` ซึ่งมี policy `p_service_all`
อนุญาตทุกอย่าง จึง **ข้าม RLS** ทั้งหมด

→ ความปลอดภัยขึ้นอยู่กับ `02_Auth.gs` ทั้งหมด ทุก API ต้องเรียก
`Auth.require(permission)` ผ่าน router ก่อนเสมอ ไม่มีทางลัด

### ชั้นที่ 2 — เมื่อเปิดให้เข้าตรง (Supabase Auth)

Policy สำหรับ role `authenticated` พร้อมใช้อยู่แล้ว 147 รายการ
อ่านสิทธิจาก JWT claim:

```json
{
  "app_metadata": {
    "org_id": "uuid",
    "employee_id": "uuid",
    "facility_ids": ["uuid", "uuid"],
    "perms": ["employee.read_facility", "leave.approve"]
  }
}
```

การเปิดใช้ทำเพียงใส่ claim เหล่านี้ตอนออก JWT — RLS จะบังคับสิทธิให้เอง
แม้แอปฝั่ง client จะเขียนผิดพลาดก็ยังเข้าถึงข้อมูลเกินสิทธิไม่ได้

### ตารางที่ยกเว้น FORCE RLS

`audit_logs`, `data_access_logs`, `login_logs`, `number_sequences`, `user_sessions`
— เพราะ trigger ที่เป็น `SECURITY DEFINER` ต้องเขียนลงตารางเหล่านี้ได้
ในนามเจ้าของตาราง ยังคงเปิด RLS อยู่ เพียงไม่บังคับกับเจ้าของ

## 4. Audit Trail

### 4.1 การเปลี่ยนแปลงข้อมูล (`audit_logs`)

Trigger `fn_audit_trigger` ติดตั้งบน 60 ตารางสำคัญ บันทึกทุก INSERT/UPDATE/DELETE:

| คอลัมน์ | เก็บอะไร |
|---|---|
| `old_data` / `new_data` | ทั้งแถวเป็น JSONB |
| `changed_fields` | เฉพาะฟิลด์ที่เปลี่ยนจริง (ข้าม `updated_at`/`updated_by`) |
| `actor_user_id` / `actor_email` | ใครทำ (จาก `fn_set_context` ที่ Apps Script ตั้งก่อนทุกคำสั่งเขียน) |
| `occurred_at` | เมื่อไร |

**เป็น append-only จริง** — trigger `trg_audit_immutable` ปฏิเสธการ UPDATE/DELETE
ทุกกรณี แม้แต่เจ้าของฐานข้อมูล (ทดสอบไว้ใน `smoke_test.sql`)

UPDATE ที่ไม่เปลี่ยนค่าจริงจะไม่ถูกบันทึก จึงไม่มี log ขยะ

### 4.2 การเข้าถึงข้อมูลส่วนบุคคล (`data_access_logs`)

บันทึกการ **เปิดดู/ค้นหา/ส่งออก/พิมพ์** ข้อมูลบุคคล พร้อมวัตถุประสงค์:

```javascript
Auth.logAccess(ctx, {
  module: 'employee', action: 'VIEW', employeeId: p.id,
  entityType: 'employees', entityId: p.id
});
```

จุดที่บันทึกอัตโนมัติ: เปิดประวัติบุคลากร, ค้นหารายชื่อ, เปิดสลิปเงินเดือน,
เปิดแฟ้มเอกสาร, ดูประวัติวินัย, ออกหนังสือรับรอง, ส่งออกรายงาน

### 4.3 การเข้าสู่ระบบ (`login_logs`)

บันทึกทั้งสำเร็จและล้มเหลว พร้อมสาเหตุ ใช้ตรวจการพยายามเข้าถึงผิดปกติ

## 5. การปฏิบัติตาม PDPA

| หลักการ | สิ่งที่ระบบทำ |
|---|---|
| **เก็บเท่าที่จำเป็น** | ฟิลด์อ่อนไหว (หมู่โลหิต, ศาสนา, ผลตรวจสุขภาพ) ไม่บังคับกรอก |
| **แจ้งวัตถุประสงค์** | คำขอเอกสารบังคับระบุวัตถุประสงค์ และเก็บไว้ใน `data_access_logs.purpose` |
| **สิทธิเข้าถึงข้อมูลของตน** | บุคลากรดูประวัติตนเองได้ทั้งหมดผ่าน self-service |
| **สิทธิรู้ว่าใครเข้าถึงข้อมูล** | API `audit.myAccessLog` — เจ้าของข้อมูลดูได้เองว่าใครเปิดดูเมื่อไร เพื่ออะไร |
| **จำกัดการเข้าถึง** | RBAC + scope + ธงข้อมูลลับรายรายการ (`is_confidential`) |
| **ตรวจสอบย้อนหลังได้** | audit trail แบบแก้ไม่ได้ |
| **ความมั่นคงปลอดภัย** | ไฟล์แนบเก็บใน private bucket เข้าถึงผ่าน signed URL อายุ 10 นาที |

### สิ่งที่หน่วยงานต้องทำเพิ่มเอง

- ประกาศนโยบายคุ้มครองข้อมูลส่วนบุคคลและขอความยินยอมตามที่กฎหมายกำหนด
- กำหนดระยะเวลาเก็บข้อมูลของผู้ที่พ้นสภาพแล้ว และวิธีลบเมื่อครบกำหนด
- แต่งตั้งผู้ควบคุมข้อมูลส่วนบุคคล (DPO) หากเข้าเงื่อนไข

## 6. ข้อควรระวังสำหรับผู้ดูแลระบบ

### 6.1 service_role key

**นี่คือกุญแจที่เปิดได้ทุกอย่างในฐานข้อมูล**

| ต้องทำ | ห้ามทำ |
|---|---|
| เก็บใน Script Properties เท่านั้น | ใส่ในโค้ดหรือ commit ลง git |
| จำกัดผู้แก้ไขโปรเจกต์ Apps Script | ส่งค่าไปฝั่งหน้าเว็บ (client) |
| หมุนเวียน key เมื่อผู้ดูแลลาออก | แชร์ทางแชท/อีเมล |

หากสงสัยว่าหลุด: Supabase → Settings → API → **Reset service_role key**
แล้วอัปเดต Script Properties ทันที

### 6.2 สิทธิ SUPERADMIN

ควรมี 1–2 คน ระบบป้องกันไว้สองชั้น:
- ถอนบทบาท `SUPERADMIN` คนสุดท้ายไม่ได้ (`admin.revokeRole`)
- ระงับบัญชีของตนเองไม่ได้ (`admin.userSave`)

### 6.3 ช่องทางสาธารณะ

หน้า `?page=jobs` และ `?page=verify` เปิดให้คนนอกเข้าถึง จึงจำกัดไว้เข้ม:
- ใช้ `PUBLIC_ROUTES` แยกจาก `ROUTES` ปกติ ไม่มีทางเรียก API ภายในได้
- คืนเฉพาะฟิลด์ที่จำเป็น ไม่คืนข้อมูลบุคลากรหรือ id ภายใน
- จำกัดการยื่นใบสมัคร 5 ครั้ง/10 นาที ต่อเลขบัตรหนึ่งใบ
- ผู้สมัครที่อยู่ในรายชื่อต้องห้ามได้รับข้อความกลาง ไม่บอกเหตุผลตรง

### 6.4 การป้องกันที่ระดับข้อมูล

| กลไก | ป้องกันอะไร |
|---|---|
| `Util.pick()` | กันการยัดคอลัมน์ระบบ (`org_id`, `created_by`) จากฝั่งหน้าเว็บ |
| `DB.remove()` ปฏิเสธ filter ว่าง | กันการลบทั้งตารางโดยพลาด |
| `Fmt.esc()` ทุกจุดที่แสดงข้อมูล | กัน XSS จากข้อมูลที่ผู้ใช้กรอก |
| CHECK constraint | กันสถานะที่เป็นไปไม่ได้ เช่นวันสิ้นสุดก่อนวันเริ่ม |
| `fn_valid_thai_id()` | กันเลขบัตรประชาชนผิดรูปแบบตั้งแต่ระดับฐานข้อมูล |
